title: Pane grid is a fixed matrix, not a split tree
tags: [grid, panes, ui, architecture]

There is no `layoutTree.ts` and no binary-split-tree `LayoutNode` anywhere in the codebase — don't go looking for one. The whole layout model is two flat things on `Workspace` (`src/shared/types.ts`): `panes: PaneSpec[]` (array order = row-major visual order) and `grid: GridTracks | null` (just column/row size *fractions*, nothing structural). Topology comes from `gridColumns(count)`/`gridShape(count)` (shared/types.ts) — a count→cols lookup for the fixed set `LAYOUTS = [1,2,4,6,8,10,12]` — not from a recursive split structure. `PaneGrid.tsx` derives each pane's `gridColumn`/`gridRow` purely from its index; the only irregularity is a "partial last row stretches to fill" adjustment (`tail`/`partial`/`tailStarts` in PaneGrid.tsx). There is no nested/arbitrary split (no 70/30 containing a further 50/50) — every workspace is a uniform matrix, resized only by dragging row/column fractions or swapping two cells' contents.

Within that model, the mechanics that move panes around are already fully generic and reusable: `movePane(workspaceId, dragId, dropId)` (store/useStore.ts) swaps two entries in `panes[]` by opaque id only; the HTML5 drag payload is `'application/x-eaon-pane'` carrying just a pane id (TerminalPane.tsx, lib/drop.ts); `setGridTracks`/`GridTracks` sizing knows nothing about what's inside a cell. See [[Pane layout: moving and resizing]] for the mechanics themselves.

What is NOT generic: `PaneSpec` (shared/types.ts) has no `kind` field at all — every field (`agentId`, `command`, `sessionId`, `status: PaneStatus`, `working`, `branch`, `contextPct`) is terminal/pty-shaped. `PaneGrid.tsx` and `TerminalGrid.tsx` render `<TerminalPane>` unconditionally for every entry in `workspace.panes` — zero indirection for "what kind of thing lives in this slot" — and `TerminalPane.tsx` unconditionally calls `terminals.attach`/`terminals.spawn` in its mount effect. So a leaf is opaque-id-based for *movement*, but hard-wired to "this is a terminal" for *content* and *rendering*.

The one existing precedent for a "kind" that changes what renders is `Workspace.kind: WorkspaceKind` (`'terminals'|'board'|'vault'|'brain'|'stats'`), switched on in `App.tsx`'s `stage()` (~line 366-379) and created via `store.openPanel(kind)`. That precedent is workspace-level and singleton-per-kind (`openPanel` finds-or-creates the one workspace of that kind — `PANEL_KINDS`/`PanelKind` in shared/types.ts and store/useStore.ts). `isPanelKind()` (shared/types.ts:81) is exported but is dead code — nothing calls it; the codebase does the same check inline instead. This workspace-level pattern answers "what does this whole tab show", not "what does this one grid cell show", so it doesn't transfer directly to pane-level kinds.

To make a grid leaf polymorphic: (1) give `PaneSpec` (or a new sibling union) a `kind` discriminant, (2) replace the unconditional `<TerminalPane>` in `PaneGrid.tsx`/`TerminalGrid.tsx` with a switch on that kind, (3) decide what "attach/detach" means for non-terminal kinds — see [[Terminals outlive React]] and [[BrowserPanel is a hard singleton; EditorPanel/GitPanel are not]] for why that matters. Also see [[Rich previews need a new binary-read IPC path]] for the file-reading side of the same research.
