A workspace can run entirely on a remote box: `Workspace.host: SshHost | null` (src/shared/types.ts). One workspace is either fully local or fully remote — panes are never mixed — which is what lets every other panel (terminals, git, worktrees, the trial bar) stay ignorant of the distinction and just pass `host` through to the same calls they already made. See [[Parallel worktrees: isolation, dirty semantics, and provisioning noise]] for the engine this builds on — every worktree function already threads an optional `host`.

**The security boundary, and why it's the only defensible one.** Eaon never sees or stores a passphrase. `src/main/ssh.ts` shells out to the real `ssh` binary for everything — terminals run it in a pty exactly like Terminal.app; `git`/`mkdir`/`test -e` run over `ssh host '<command>'`. If a key needs unlocking, the prompt happens inside that real `ssh` process on the real pty; Eaon's code never touches the key or the passphrase. `sshArgv()`/`remoteCommandLine()` are pure functions (given a host, return exactly the argv/string that would run) — proven in `scripts/check-ssh.mjs` with a fake `ssh` on `PATH` that records what it was actually invoked with, and a second fake that instead *executes* the trailing command for real (`scripts/check-ssh-worktrees.mjs`) — real git isolation, dirty semantics and merge, all over the "remote" path, no actual second machine needed.

**Two boundaries inside the connection layer, deliberately different.** The `ssh` argv itself (host, `-i`, `-p`, …) never crosses a shell — `execFile`/`node-pty` pass it straight to exec, so nothing needs escaping. The one exception is the trailing remote-command string, which sshd *does* hand to the remote user's shell — every argument in it goes through `remoteCommandLine()`'s POSIX single-quoting. Getting the two confused is the whole risk surface here; `remoteHomeDir()` is the one narrow, explicitly-commented exception that sends a raw unquoted snippet (`printf %s "$HOME"`), because resolving `$HOME` requires shell expansion — safe only because the snippet is a fixed string in the source, never built from a host label or a path.

**~/.ssh/config is read for the picker, never modified, never fully re-implemented.** `parseSshConfig()` only extracts top-level `Host` blocks with no wildcard in the pattern; `Include` and `Match` are not followed — getting ssh_config's own resolution order slightly wrong would be worse than a picker that's missing an entry, since a host that looks connectable here but resolves differently for real `ssh` is a trap. A config-sourced host always connects **by alias** (`ssh nas`), never by re-stating the fields Eaon parsed out of the file, so `ProxyJump`/multiple `IdentityFile` lines/anything else in the user's real config keeps working exactly as it would from a terminal.

**What "remote" actually touches, machine-by-machine:** `pty-manager.ts` branches `spawn()` on `req.host` — local behavior is byte-identical to before this existed. `git.ts` and `worktrees.ts` both keep every local `fs`/`execFile` call untouched and add a remote branch that dispatches early, specifically so the 65 pre-existing local worktree tests could never regress (verified: they didn't, twice, including through a `dirForRepo` signature that had to become `async` for the remote case). `brain/register.ts`'s `provisionWorkspace` is explicitly skipped for a remote pane in the `pty:spawn` handler — `req.cwd` is a path on the far end, and treating it as local would risk writing Eaon's memory-provisioning files to a coincidentally-matching local path.

**What's deliberately not built yet, stated rather than silently missing:** no SFTP-backed file editing (EditorPanel/FilesPanel are local-only), no port forwarding for the browser panel, no auto-reconnect on a dropped connection, and remote session resume/observation is a no-op (every remote pane launch is treated as fresh — safe, just not smart, since Eaon has no way to see a remote box's own Claude transcripts).

**A real bug the live UI check caught that the engine tests couldn't:** the "Remote host" tab in the setup wizard used `draft.host` both as "which panel to show" and "which host is chosen" — clicking the tab never set a host, so `aria-selected` never flipped and the host picker could never appear. `check-ssh.mjs`/`check-ssh-worktrees.mjs` had no way to catch this since it's pure UI wiring; only driving the actual rendered wizard did. Fixed with a separate `showRemote` local state, decoupled from whether a host has actually been picked.
